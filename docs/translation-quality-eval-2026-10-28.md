# 日英同時通訳 比較評価（2026-10-28）: 現行 translate / gpt-live-1 / realtime VAD / cascade 試作

追跡 Issue: [#21](https://github.com/niho-life/niho-translate/issues/21)。測り方の設計は [translation-quality-research.md](translation-quality-research.md)、ハーネスの契約は [research/eval/README.md](../research/eval/README.md)。この文書は**数値と分類だけ**を載せる。音声・原文・訳文・実データの path は私有フォルダにあり、公開しない。

## 1. 結論

- **現行の `gpt-realtime-translate`（A）は最速・最安。** 日本語の節の発話開始→その意味を担う英語音声の開始（`L_start`）は P50 5.3 秒・P95 9.4 秒、8 秒以内が 85%。節の終わりからは P50 −0.5 秒（話し終わる前に英語が始まる）・P95 3.5 秒。ただし意味の評価は 3 候補中で低く、重大誤り（数・時刻・否定・地名・主体・条件の反転／創作）が 244 区間で 20 件、訳抜け 30 件、創作 19 件。
- **`gpt-live-1` + 公式の通訳専用 prompt（B）は意味が良い。** 意味 2.38〜2.50（A は 2.18）、意味が崩れた区間（0〜1 点）19〜22%（A 31%）、重大誤り 4〜6 件、訳抜けは公式 prompt のみの条件で 8 件/120 区間。代わりに `L_start` は P50 +0.5〜1.0 秒・P95 +1.3〜1.7 秒、8 秒以内 76〜79%、費用 1.5 倍（$0.05/分）。音声は無音も含む連続ストリームで届く。
- **背景・用語集の効果は今回の 3 窓では見えなかった**（公式 prompt のみの方が意味は同等以上。地名の誤りは用語集あり 0 件・なし 2 件だが run 間のばらつきの範囲内）。
- **`gpt-realtime-2.1` の semantic VAD 通訳（B2）は不採用水準。** 長い発話を待ってから一括で話す（P50 32 秒、訳抜け 60 件/120 区間、理想再生 queue 最大 46 秒）。
- **cascade 試作（D'）は現形では不採用。** 各段は速い（ASR 最初の文字 0.7 秒、LLM 最初の token 0.63 秒、TTS 最初の音声 0.52 秒）が、英語の発話量が原音と同等以上（300 秒の日本語に 234〜318 秒の英語）で直列の読み上げが追いつかず、`L_start` P50 10.5 秒・8 秒以内 19%。速い話者では終了時に 37 秒分がまとめて出た。直接音声モデルは訳を圧縮している（A は 300 秒に 154〜223 秒）。
- **現行 A で 2 つの事故を観測した。** (1) 10 run 中 1 run で、2 分間ほど**訳音声が訳字幕と別の内容**になった（ASR 語と字幕の一致率 21%・38%。別の ASR でも同じ結果。再実行では再現せず）。聞き手には字幕と違う英語が流れる。(2) 発話の切れ目で訳音声がまとめて届き、理想再生 queue が 3.3 秒に達した run があった。iOS の未再生保持上限 2 秒（terminal overflow）を超える。

判断順 Q（意味）> D（単純さ）> C（費用）に従うなら、**A を基準経路に残しつつ B の製品 adapter を作って実機受入（#5）で並走させ、人が訳音声を聴いて決める**のが次の一手。A の 2 つの事故は B の採否と独立に P1 で扱う。

## 2. 測り方

- 素材: 利用承認済みの日本語会話録音（2 話者、約 33 分）の 5 分窓 × 4（`src1-w1`〜`w4`。w1/w2 は 20 秒、w2/w4 は 40 秒重なる）と、別の録音（講演調の 1 人語り）の 5 分窓 × 1（`src2-w1`）。すべて日→英。
- 送信: 24 kHz mono PCM16 を実時間で送る（200 ms。製品と同じ 100 ms も A で比較）。窓の後に 6 秒の無音を送り flush。
- 訳音声は到着時刻どおりに置いた `output-timeline.wav` にし、理想再生モデル（到着したら途切れず再生）で `queueMs` を出す。
- 正解原稿: whisper-1 の単語時刻・`gpt-4o-transcribe-diarize`・ローカル whisper.cpp を照合し、録音付属の人手未校正転記で直した**節単位の区間**（計 222 区間、statement/question 204。長さ P50 6.7 秒・P95 10.7 秒・最大 13.5 秒。**8 秒より長い区間が 61（30%）**）。数・時刻・否定・地名・固有名詞・条件・主体・時制を fact として注釈。人は未試聴。未確定 19 区間。
- 判定: `output-timeline.wav` を有声区間ごとに whisper-1 で単語時刻化し、LLM（gpt-5.4）が各区間に対応する**最初の意味を担う英単語**を選ぶ。時刻・遅延・集計はコードで決定。意味は 0〜3（3 = 文意が伝わる、2 = 軽い欠落だが事実は正しい、1 = 重要部分の欠落／誤り、0 = 誤訳・訳なし・創作）。fact は ok / wrong / omitted。flags は訳抜け・創作・質問に答える／陳述化・重複・言語違い・不明瞭。
- `L_start` = 英語の開始 − 区間の発話開始、`L_end` = 英語の開始 − 区間の発話終了。backchannel は遅延統計から除外。未訳は分母に残す。
- 判定の再現性: 3 run を同じ ASR 結果で 2 回判定。集計の P50 差 ≤ 0.5 秒、意味平均の差 ≤ 0.1、区間ごとの意味が一致 36〜38/44（±1 以内 42〜44/44）、開始語が同一 31〜37/42（1 秒以上ずれたのは 0〜3）。重大誤りの件数は 2→0 と動いた run があり、1〜2 件の差は読まない。
- 判定器も ASR も OpenAI のモデル。OpenAI 製エンジンの比較に同系統の偏りが入り得る。

### run 間のばらつき

同じエンジン・同じ窓を 2 回流すと、意味平均は 0.1〜0.3、`L_start` P95 は 1〜3 秒動く（A w1: 2.38→2.30、P95 9.5→11.9 秒。B w1: 2.13→2.45、P95 10.5→8.6 秒）。A 100 ms w2 は 1.39→2.21（1 回目は §4 の事故）。1 run・1 窓の差で優劣を決めない。

### 遅延の構造

- A・B とも節の終わりより前に英語が始まる（`L_end` P50 ≤ 0.3 秒）。`L_start` の遅い側（P95 9〜11 秒）は、原稿の区間が長いこと（P95 10.7 秒、30% が 8 秒超）が主因で、モデルが述語を待つぶんは `L_end` P95 の 3.5〜5.6 秒。「発話開始から 8 秒」を全区間で満たすには述語より前に訳を出す必要があり、否定・条件を誤る方向になる。評価は `L_end` も併記して読む。
- A は 100 ms と 200 ms で `L_start` の差なし。200 ms（公式推奨）でよい。
- B2 は turn の終わりまで待つので長い発話に向かない。D' は段の遅延より発話量が律速。

## 4. 観測した事故と品質の型

- **A: 訳音声と訳字幕の不一致（1/10 run）。** 100 ms w2 の 1 run で、3〜4 分目の ASR 語と字幕の一致率が 21%・38%（他の分は 98〜100%）。別の ASR（gpt-4o-transcribe）も whisper と一致し字幕と不一致。再実行では 99%。製品では字幕が正しく音声だけが別の英語になる形で聞き手に届く。再現率と条件は未特定。
- **A: 発話の切れ目のまとめ出し。** 200 ms w1 の再実行で、窓の末尾の無音直後に 3.1 秒＋2.0 秒の音声が 2 秒以内に届き、理想 queue 3.3 秒・2 秒超の chunk 13。iOS の保持上限 96,000 byte（2 秒）を超え、現行実装では terminal overflow になる。同じ窓の 1 回目は 0.7 秒。
- **D': 読み上げと字幕の不一致。** w4 の 2 分で一致率 48%・51%（原因未特定）。速い話者（src2）では内部の積み残しが終了時に 37 秒分出た。
- **全エンジンに共通の型。** 質問を一人称の陳述に変える（A 9+7、B 6+4、D' 9 件）。長い発話の中の 1 節の訳抜け。期間の「〜年半」を「〜年半前」と訳す。節末の否定の脱落（B で 1〜3 件、A で 5 件）。施設・地名の誤訳（A 4 件、B 公式のみ 2 件、B 背景＋用語集 0 件）。

## 5. 推奨と次の工程

1. **A を基準経路に残し、P1 を先に直す。** (a) iOS の再生保持上限 2 秒は発話の切れ目のまとめ出しで超える。上限を 4〜5 秒にするか、overflow を terminal にせず古い無音から落とす設計へ（#5 の実機受入前）。(b) 音声・字幕不一致の再現率を測る（A を同じ窓で 10 run 以上）。合成音声で再現できれば OpenAI へ報告する材料にする。
2. **B の製品 adapter を作り、#5 の実機受入で A と並走する。** adapter 境界は `TranslationFactory`（話者別セッション・private route・lease・ACK・本文非保存を維持）。B は無音も含む連続音声を返すので、relay の送信量と iOS の queue 挙動が A と変わる。60 分の session 寿命・再接続は未確認。
3. **B の prompt を同じ窓で A/B する。** 質問を質問として訳す指示、地名のローマ字固定、背景の有無。1 条件 3 窓 × 2 run 以上。
4. **人が聴く。** 私有フォルダの `mixed.wav`（L＝原音、R＝訳音声）を A と B で聴き比べ、判定器の意味採点が人の感覚と合うかを確認する。合わなければ判定基準を直してから次の比較へ。
5. **B2 と D' は閉じる。** D' を再開するのは、英語の発話量を抑える訳し方（要約的な同時通訳）と読み上げ速度の制御を入れても直接音声モデルに勝つ見込みが数値で示せる場合だけ。

## 6. 費用

実測の推定: A $0.17/5 分、B $0.28/5 分、B2 $0.21〜0.40/5 分、D' $0.28〜0.34/5 分（LLM は Fast mode）。判定は 1 run あたり約 $0.3（whisper-1 ＋ gpt-5.4）。今回の計測・判定・原稿作成の合計は約 $30。

## 7. 未検証

実 iPhone 2 台・private headset での耳到達時刻、人手の意味評価、B の 60 分耐久と session 寿命、A の不一致事故の再現率、DeepL Voice（鍵・実録音の送信許諾なし）、英→日方向。

### 8.2 判定器の確認

- 判定モデルを OpenAI 以外（Antigravity 経由の Claude / Gemini）でも動かせるようにした（`--judge-backend agy`）。合成 6 区間では gpt-5.4 と全区間一致。実 run（A の w1、44 区間）を `gemini-3.8-flash-high` で判定した結果は gpt-5.4 と意味平均 2.35 vs 2.30、区間ごとの意味が一致 33/44（±1 以内 42/44）、開始語が同一 35/43、重大誤り 1 vs 3。OpenAI の判定器が OpenAI のエンジンを甘く採点している兆候はない（Gemini の方がわずかに高い）。Claude での判定は Antigravity の利用枠が尽きて未完（約 1 週間で回復）。1 run の判定に約 17 分かかる。
- 正解原稿の本文は whisper-1・gpt-4o-transcribe-diarize・whisper.cpp と録音付属転記の 4 系統を gpt-5.4 が照合したもの。Gemini での文字起こしは、Antigravity CLI が音声ファイルを読む手段を持たず、Vertex AI も未有効化のため未実施。

### 8.3 決定と実装

- 訳音声の声: オーナーが 4 声（marin / cedar / coral / sage）の同じ区間の訳を聴き、**marin** に決定（2026-10-28）。
- `gpt-live-1` の製品 adapter（`packages/provider-openai-live`）を追加し、relay-local の `TRANSLATE_PROVIDER=live` で切り替え可能にした。現行 provider と同じ上限・無音規則・drain・health ping。fake transport テスト 26 件、合成音声の実 API smoke で `session.started` 0.76 秒・字幕と音声の受信・`session.closed` を確認。**GPT-Live は会話モデルで文脈が蓄積し、評価データの使用率から約 42 分で上限に届く見込み**。60 分運転にはセッションの切り替えが要る（未設計）。原文字幕が常に届くので、話者本人の画面での扱いを iOS で確認する必要がある。
- iOS の再生待ちを 2 段上限にした（soft 2.0 秒で観測通知、hard 5.0 秒で未 schedule の完全無音→古い音声を落として継続）。`onPlaybackOverflow` は `onPlaybackPressure` に置き換え。swift test 40 件・iOS 15.5 typecheck 通過。実機での既定値の妥当性は未検証。
- 研究・製品の調査: [simultaneous-interpretation-landscape-2026.md](simultaneous-interpretation-landscape-2026.md)。日→英の直接音声翻訳を公開評価した研究は無く、近い言語対の長文でも平均遅延 5.6〜7.3 秒。次に比べる直接音声の候補は Gemini 3.5 Live Translate（日英対応・指示不可）、用語集の効果を見るなら DeepL Voice。

### 8.4 B の prompt 条件の A/B（w1〜w3、各条件 2 run、`-q` = 質問を質問のまま・話者の人称を保つ・地名はローマ字の規則を追加）

| 条件 | run | 区間 | `L_start` P50 / P95 | 意味 | 意味 ≤1 | 重大誤り | 訳抜け | 創作 | 質問が質問として伝わった（意味 ≥2 / 質問区間） |
|---|---:|---:|---|---:|---:|---:|---:|---:|---:|
| 公式 prompt のみ（plain） | 6 | 240 | 6.3 / 10.8 s | 2.55 | 17% | 8（地名 3・否定 3） | 14 | 7 | 9 / 30 |
| plain + `-q` | 6 | 240 | 6.2 / 11.2 s | 2.55 | **14%** | **3** | **7** | 10 | **14 / 30** |
| 背景＋用語集 | 4 | 160 | 5.8 / 11.0 s | 2.36 | 22% | 4 | 8 | 3 | 5 / 20 |
| 背景＋用語集 + `-q` | 6 | 240 | 5.9 / 11.2 s | 2.53 | 16% | **3** | 14 | 6 | **14 / 30** |

- `-q` 規則は質問の保持を 25〜30% → 47% に上げ、重大誤りを 8 → 3（plain）に減らした。遅延は変わらない。判定器の `answered_question` flag の件数（6〜8）は条件間で差がなく、質問の扱いの改善は意味採点の側に出ている。
- 背景・用語集の有無は意味平均に効かない（2.53〜2.55 vs 2.36〜2.53。run 間のばらつき ±0.25 の中）。地名の誤りは用語集あり 1 件・なし 3 件で、効果はあり得るが件数が少ない。
- 推奨: 製品 adapter の既定は `plain-q`（拠点ごとの用語集は host が足す）。背景＋用語集は拠点の固有名詞が多い場で `domain-glossary-q` を使う。いずれも 1 条件 6 run・240 区間の値で、run 間のばらつきより大きい差だけを読んだ。

### 8.5 原稿の第 4 系統を Gemini に替えた再判定（同日）
