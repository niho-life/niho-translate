# 公開音声による日英同時通訳のソフトウェア評価（2026-10-29）

## 目的と結論

実機がない段階で、公開済みの長尺日本語音声を実時間の速度で流し、意味の保存と「日本語の意味単位の開始→対応する英語音声の開始」を測る。評価単位は約5分の連続窓とし、途中でエンジンをリセットしない。

今回の結果だけでは、5～8秒以内に高精度の通訳を**安定して**開始できる構成は確認できなかった。`gpt-live-1` の標準指示は意味を比較的よく保存したが演説では遅く、早出し指示は一部で速くなっても欠落・幻覚が増え、別窓では速度改善が再現しなかった。短い背景注入は不動産対談の同一5分窓3回で意味を改善する兆候があったが、p95の速度目標は3回中1回しか達成せず、重大な意味の取り違えも残った。`gpt-realtime-translate` と Gemini の通訳専用モデルは速いが、意味の取り違えが品質上の制約になった。Qwen3.8 LiveTranslateも公開演説では8秒以内96%と速かったが、意味の欠落と再生待ちがあり、別録音では速度が落ちた。さらに[自然な対談5分の比較](#自然な日本語対談5分の比較と構成判断2026-10-30)では、Qwenの訳音声が原音声より35～83秒長く、区切り方式を変えても再生待ちは最大39秒以上だった。精度優先の製品既定は当面`gpt-live-1 plain-q`とし、5～8秒目標を達成したとは扱わない。

追加した[短文75件の独立評価](#独立した日本語読み上げ75件の誤訳監査2026-10-29)ではQwenが最も原文の意味を保った。ただし読み上げ短文をつないだ試験であり、上記の連続音声と評価対象が異なる。自然な対談ではQwenの再生待ちが蓄積したため、短文の結果だけでモデルを切り替えない。

## 評価方法

24 kHz PCMのWAVから5分窓を選び、200 ms単位で入力する。英語音声を理想再生タイムラインに配置し、出力音声を単語時刻付きで再文字起こしした。先行評価は `whisper-1`、今回追加した音声再評価はローカル `whisper.cpp small.en` を用いる。区間ごとに判定モデルが原文の意味に対応する英単語を選び、その最初の時刻から原文区間の開始時刻を引いた値を `lStart` とした。これは「我が…」から "Our company…" までに相当する指標で、入力音声の窓開始からの単純な処理時間ではない。実端末のマイク・Bluetooth・OS再生は含まない。

意味スコアは0（不成立）～3（十分に伝わる）。先行評価はClaude、今回追加した音声再評価はCodex app-serverの同一モデルによる判定で、両者の意味スコアを同条件のA/Bとして直接比較しない。`within8s` は意味のある原文区間のうち、対応する英語の最初の語が開始から8秒以内に聞こえる割合。p50/p95は対応した区間の値で、欠落区間は割合の分母に残す。サンプル数が小さく、同じ録音へのプロンプト最適化は過学習しやすい。重大誤りの自動件数は意味の取り違えを網羅しないため、個別の訳文も必ず確認する。

### J-WAVE 540–840秒の安価な暫定判定

両条件とも5分の実時間リプレイを最後まで実行し、音声出力は標準304.1秒、早出し296.1秒で、出力キューの最大はそれぞれ0.39秒、0.37秒。英語音声の再文字起こしにはAPIを使わず、**エンジンが出した英語字幕**をCodex app-serverの同一モデル（`gpt-5.6-sol`）で39採点区間に対応づけた。

| 研究用指示 | 字幕に対する意味平均 / 3 | 重大な事実の誤り | 幻覚フラグ | 字幕到着の代理 `lStart` p50 / p95 | 字幕8秒以内 |
|---|---:|---:|---:|---:|---:|
| 標準 | 2.67 | 3（うち1件は参考原稿が不確か） | 5 | 5.53 / 11.74秒 | 87% |
| 慎重な早出し | 2.90 | 0 | 2 | 5.37 / 10.01秒 | 79% |

この窓では早出し指示の字幕品質が良かったが、演説の後半5分では速度改善が再現せず、前半と不動産対談では幻覚・欠落が残った。J-WAVEの数値は**英語音声の内容確認や発話開始時刻の測定ではない**。標準の誤り2件は参考原稿が「不確か」としていない区間で、別の1件は不確かな区間だった。製品指示の採用判断は音声の再文字起こしまたは聴取確認を伴う反復試験まで保留する。

### J-WAVE窓の英語音声による再評価

上の字幕代理値を検証するため、出力した英語WAVをローカルの `whisper.cpp` と [公式配布の `small.en` モデル](https://github.com/ggml-org/whisper.cpp/blob/master/models/README.md)で有声区間ごとに読み直した。字幕をASRのpromptへ渡さず、無音上の語を除外した。モデルのSHA-1は公式一覧と一致する。単語とエンジン字幕の一致率は標準99%、早出し96%で、差が残る箇所の音声聴取は未完了である。別の5分窓で有料 `whisper-1` とローカルASRの完全一致649語を比較すると、語頭時刻の差（ローカル－有料）はp50 −0.08秒、5～95パーセンタイル −0.51～+0.35秒だった。両ASRとも人手で正解時刻を付けたものではないため、ここでの秒数はソフトウェア上の推定値である。

標準指示は英語**音声**の単語に対してCodexで39区間を再判定した。意味平均2.69/3、重大な事実誤り2件（うち1件は参考原稿が不確かな区間）、幻覚4件。`lStart` はp50 **7.94秒**、p95 **13.52秒**、8秒以内 **49%** だった。字幕代理では8秒以内87%だったので、字幕時刻を音声レイテンシに使うと大幅に過大評価する。対応する単語の「音声時刻－字幕到着時刻」は標準でp50 **2.25秒**、p95 **6.63秒**。早出しではp50 **0.65秒**、p95 **1.28秒**だった。これらは一致した単語についての値で、字幕と音声の差を示す。

この3条件の音声再生キュー最大は0.37〜0.45秒だった。一方で字幕から音声までの遅れは最大側で数秒ある。Timekettleの特許にある未再生音声の倍速処理は、**生成済み音声がキューに溜まる場合**には有効な候補だが、この録音の主な遅れを消せない。訳音声の生成開始と意味単位の確定を改善する必要がある。

早出し指示の字幕判定を同じ音声ASR単語へ機械的に対応づけると、39採点区間中33区間で両端の語が一致し、対応区間の `lStart` はp50 **5.86秒**、p95 **11.14秒**だった。**6区間を対応不能として除外した暫定値**であり、字幕に対する意味判定を流用している。音声を直接判定した標準指示の値と同列の合否判定には使わない。演説の後半窓では早出しの遅延が悪化しているため、製品既定には昇格させない。

この窓の日本語意味区間39件は、長さのp50が6.55秒、p95が10.81秒で、12件は8秒を超える。述語・否定まで常に待つ方式だけでは、発話開始8秒以内を全区間で達成できない。意味の確定前に音声を出すと取り消せないので、達成には安全な先行訳と事実誤りの厳格な検査を両立させる必要がある。発話開始からの8秒は品質との同時条件として扱う。

### Qwen3.8 LiveTranslateとの同一窓比較

Alibaba Cloud Model Studioシンガポールで研究用APIキーを対象モデルだけに制限し、無料枠の超過時停止を有効化した。`qwen3.8-livetranslate-flash-realtime`へ同じJ-WAVE 540–840秒のWAVを200 ms刻みで5分間流した。Qwenは16 kHz PCM入力・24 kHz PCM訳音声出力で、原文と訳文の字幕も返す。以下は両エンジンの**実際の英語音声**を同じローカルASR（`small.en`）と同じCodex判定器で採点した1回ずつの結果。モデルには公開音声だけを送った。

| 同一5分窓 | 意味平均 / 3 | 重大事実誤り / 幻覚 / 欠落 | `lStart` p50 / p95 | 8秒以内 | 訳音声の再生待ち最大 / p95 |
|---|---:|---:|---:|---:|---:|
| GPT-Live `plain-q` | 2.69 | 2 / 4 / 0 | 7.94 / 13.52秒 | 49% | 0.39 / 0.39秒 |
| Qwen3.8 LiveTranslate `speaker_detection` | 2.51 | 0 / 3 / 1 | 9.26 / 13.65秒 | 33% | 12.34 / 10.79秒 |

Qwenの英語音声を再文字起こしした約735語は、エンジンの英語字幕と99%一致した。訳文の大部分は意味が分かるが、主語の変化、原文にない補足、重要句の欠落が残る。自動判定の重大誤りが0件でも、40区間の人手確認済み合格を意味しない。出力音声の総量はQwen約270秒、GPT-Live約304秒。Qwenは5分間の各1分帯で最大約5～12秒の再生待ちが発生し、iOS経路の2秒保持上限を超える音声deltaが682件あった。デジタル完全無音の200 ms以上の連続は無く、既存の無音除去では解消しない。

Qwen公式の別設定`server_vad`も同窓の冒頭60秒で疎通したが、再生待ち最大11.50秒、p95 9.28秒で、話者検出を使った5分runの最初の1分（最大5.30秒）より悪かった。60秒1回のみの結果で品質差は未採点。5分runの音声到着時刻とbyte数を固定して、再生だけを仮に1.25倍にした場合でも最大待ちは約5.82秒、1.5倍でも約3.83秒だった。これは聞き取りやすさを無視した机上計算であり、倍速だけでは2秒上限に届かない。現状のQwenは製品の5～8秒目標と2秒再生保持上限を満たさず、既定エンジンに採用しない。出力ペース・音声再生制御・別録音での再現性を優先して調べる。

原文字幕も参考原稿と暫定照合した。全区間を連結し、UnicodeをNFKC正規化して英字を小文字にし、句読点・空白を除いた後の文字編集距離を原稿文字数で割った。J-WAVEではQwen 11.1%、GPT-Live 11.0%（原稿1,767文字）、公開会見30–330秒ではQwen 7.1%、GPT-Live 3.4%（940文字）。これは人手校正済み音声認識誤り率ではない。原稿の不確かさ、言い淀み、表記揺れも数えるが、少なくともこの2録音でQwenの日本語文字起こしが明確に優れる根拠はない。

### 独立した公開会見30–330秒での再現確認

同じ会見WAV・参考原稿29区間に対し、Qwenと既存GPT-Live `plain-q` の実際の英語音声を同じローカルASR・Codex判定器で読み直した。元のGPT-Live runは再生せず、保存済み音声を再採点した。以下も各条件1回で、人手聴取による採点ではない。

| 同一5分窓 | 意味平均 / 3 | 重大事実誤り / 幻覚 / 欠落 | `lStart` p50 / p95 | 8秒以内 | 訳音声の再生待ち最大 / p95 |
|---|---:|---:|---:|---:|---:|
| GPT-Live `plain-q` | 2.86 | 0 / 0 / 0 | 10.20 / 24.32秒 | 32% | 0.41 / 0.28秒 |
| Qwen3.8 LiveTranslate `speaker_detection` | 2.21 | 1 / 2 / 5 | 5.39 / 7.30秒 | 96% | 5.66 / 4.31秒 |

Qwenはこの会見では速いが、「私」という主体や立場が抜け、将来の5年間を過去5年間の実績として訳す箇所があった。目標を達成済みの事実に変えた箇所もあり、上表の重大誤り件数だけでは品質問題を表しきれない。参考原稿に不確かさのある区間を除いた12区間でも、意味平均はQwen 2.08、GPT-Live 2.83だった。Qwenの訳音声総量は約223秒、GPT-Liveは約299秒だが、長さだけから欠落の原因は断定しない。Qwenの再生待ちを出力到着時刻を固定して仮に1.5倍速で再計算しても最大約3.32秒で、2秒の保持上限は超える。2つの公開録音でQwenの速度・品質・再生待ちのバランスが変わったため、単一runの速さを製品性能と扱わない。

[GPT-Liveの公式プロンプト資料](https://developers.openai.com/api/docs/guides/live-prompting)にある発話ペース指示も、研究用 `brisk-q` として同じ5分窓で試した。出力音声の総量は302.5秒で標準の304.1秒とほぼ同じ。英語ASRは693語、字幕との一致率99%で、単語の「音声－字幕」はp50 1.16秒、p95 3.41秒だった。一部の時代表現の取り違えと列挙内容の欠落をサンプル確認したため、品質優先の製品設定には採用しない。これらはプロンプトだけで15%の発話速度を保証できないことも示す。

## 研究用プロンプトで分かったこと

`compact-q` は短く訳して待ち行列を抑える実験。意味が落ち、幻覚や欠落も増えたので採用しない。`early-safe-q` は「意味が確定した最短の安全な節を出すが、否定・数・固有名詞・動詞が未確定なら待つ」と指示した実験。同じ演説の前半ではp50が短くなったが、後半で逆転した。早出しのタイミングをプロンプトだけで安定制御できるとは言えない。どちらも研究ハーネス内の指示で、製品の既定設定は変更していない。

### 背景情報の注入

`gpt-live-1` の研究用 `contextFile` には、会話の話題・登場人物・地域を短く記し、「音声で発話していない事実を足さない」指示を付けた。本文は非公開フォルダにだけ保存した。原録音の冒頭60秒を背景なし／ありで各1回流すと、背景なしでは原文字幕から話者名が抜け、英語音声にも出なかった。背景ありでは原文字幕に話者名が現れ、英語音声のローカルASRにもその名前が1回現れた。**固有名詞の改善候補が1回見えた**という結果であり、反復性や人手での聞こえ方は未確認である。

同じ非公開録音の別の連続5分窓（150–450秒）を背景ありで評価すると、実際の英語音声の意味平均は2.65/3、重大な事実誤り0、幻覚フラグ3、欠落フラグ2。`lStart` はp50 **7.54秒**、p95 **18.87秒**、8秒以内 **53%** だった。背景なしの既存2回は別の判定モデルによる値なので意味スコアを直接比較できないが、背景ありで5～8秒の遅延目標を満たしたとは言えない。この5分窓の発話には背景に記した人名・地域名がほぼ出ないため、用語補正の有効性を検証する窓としては弱い。背景情報による話題の決めつけや出力の長文化も監視する必要がある。

より話題に近い別の連続5分窓（690–990秒）では、既存の背景なし音声と新しい背景あり音声を、同じローカルASRと同じCodex判定器で40区間ずつ評価した。どちらも研究用 `domain-glossary` 指示を共通に使った。英語**音声**の集計は次の通り。

| 690–990秒 | 意味平均 / 3 | 自動の重大事実誤り | 幻覚 / 欠落フラグ | `lStart` p50 / p95 | 8秒以内 |
|---|---:|---:|---:|---:|---:|
| 背景なし | 2.35 | 2 | 1 / 1 | 4.96 / 8.58秒 | 90% |
| 背景あり | 2.58 | 0 | 2 / 3 | 5.10 / 7.23秒 | 95% |

背景なしの重大誤り2件には明確な否定反転が1件あり、もう1件は謝罪表現の誤訳を評価原稿が「否定」に分類したものだった。背景ありではその2区間の意味が正しく伝わった。一方、背景ありには欠落・不要な補足が増えた。参考原稿に不確かさを付けた4区間を除いた36区間でも、意味平均は背景なし2.39→背景あり2.69、p95は8.84→7.32秒、8秒以内は89→97%だった。**ただし各条件1回**であり、原文字幕の文字列一致率も約92%にとどまる。この初回比較を根拠に製品既定を変更しない。

同じ窓をさらに**背景なし2回・背景あり2回**、背景なし→あり→あり→なしの順に実時間リプレイした。初回と合わせ各条件3回の音声を、同じローカルASR・Codex判定モデル・40区間の参考原稿で評価した。次の中央値と範囲は**run単位**で計算し、同じ音声の120区間を独立した別会話と見なしていない。

| 690–990秒、各3回 | 意味平均 / 3：run中央値（範囲） | 自動重大誤り：3回合計 | `lStart` p50：run中央値 | `lStart` p95：run中央値（範囲） | 8秒以内：run中央値（範囲） |
|---|---:|---:|---:|---:|---:|
| 背景なし | 2.35（2.05～2.48） | 7 | 5.40秒 | 10.54秒（8.58～12.01） | 85%（75～90%） |
| 背景あり | 2.58（2.43～2.58） | 2 | 5.85秒 | 11.65秒（7.23～12.96） | 80%（35～95%） |

背景ありの意味スコアは3組の比較で2組が改善、1組はわずかに悪化。p95は1組だけ改善し、2組で悪化した。背景ありでp95≤8秒は**1/3回**、自動重大誤り0件は**2/3回**。原稿の事実型には謝罪表現を「否定」とした分類誤りがあり、重大誤り件数を人手で完全確認した値とは見なさない。残る誤りには主体を別人へ変えた訳や過去の出来事を仮定に変えた訳がある。追加4回の音声ASRと字幕の語一致率は98.7～99.6%、音声再生キュー最大は0.39～1.30秒。背景ありの語数は683～782語、背景なし696～723語で、初回に見えた長文化も一定ではなかった。背景ありの速い回と遅い回を比べても字幕→音声の語時刻差中央値は0.95秒と1.09秒で、数秒の`lStart`差は主に再生キュー後段では説明できない。初回と同じ別窓150–450秒では背景ありで遅延が悪化した。

### 追加の無課金分析：遅延の長い区間

同じ5分窓の6runについて、40採点区間×6回のうち訳音声の語へ対応できた231件を、原文区間の長さ別に再集計した。5秒以下58件では`lStart > 8秒`が8件、5秒超～8秒101件では22件、8秒超72件では17件だった。訳音声が**原文区間の終端より前**に始まった割合はそれぞれ4/58、62/101、62/72。現行モデルも長い区間の終わりを常に待っているわけではない。ただし先に出た英語が後続の重要事実まで正しく表しているかは、この集計からは分からない。

6runのうち1runでは、対応できた38区間の24件が8秒超で、5つの各1分帯の`lStart`中央値は6.99～10.17秒だった。このrunの理想再生キュー最大は0.39秒、訳音声総量は300.54秒。連続した遅れは文の長さや再生キューだけでは説明しきれず、出力する意味単位の選び方・モデル側の時刻変動・語対応の誤りを分離して調べる必要がある。**同一録音の反復は独立した会話サンプルではなく、参考原稿と語対応も人手校正前**である。未対応9件を遅延分布から除き、8秒達成率の分母には残す。

この比較の共通指示は研究用 `domain-glossary` で、Node版relayの製品既定 `plain-q` ではない。話者の人称を保つ規則なども異なる。製品の背景注入は、現在の結果だけで採用しない。次は製品既定指示を固定した別録音での反復と、日英話者による実音声の否定・主体・欠落の確認を優先する。

優先して試す案は、(1) 少数の重要事実について原語と訳音声の語時刻を人手校正し`L_fact`を測る、(2) 製品既定`plain-q`と[公式の短い通訳指示](https://developers.openai.com/api/docs/guides/live-prompting)を独立した複数の公開録音・複数runで比較する、(3) 固有名詞だけの短い背景と話題説明を別条件で比較する、(4) マイク・騒音・話者重なりの入力条件を固定した録音群で頑健性を試す、(5) 単一セッションの別エンジンと英日方向を同じ基準で比較する、の順。品質のゲートは平均スコアだけでなく、事実誤り・欠落・幻覚・意味を逆転する誤訳を個別に置く。発話区切りをアプリ側で明示的に制御するには、現在のGPT-Live直結経路にはない途中認識と出力確定の制御点が必要で、別構造の研究課題として扱う。プロンプト変更だけで8秒以内と正確性の両立を保証しない。

## サブスクリプション枠とAPI費用

[OpenAIのCodex app-server資料](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server)に沿い、ChatGPTログイン済みのローカル `codex app-server` をテキスト判定に利用できる。研究ハーネスに `--judge-backend codex` を追加した。既存の音声単語時刻を再利用する `--skip-asr` と組み合わせると、判定LLMのAPI呼び出しを避けられる。`--word-source subtitle` は音声ASR自体を呼ばず、エンジン字幕の到着時刻と本文から暫定判定する。**このモードの遅延は英語発話の遅延ではなく字幕到着の代理値**であり、字幕と実音声の不一致も評価できない。

演説の最初の5分窓は、既存の音声単語時刻を使い、Codex app-serverの `gpt-6-astra` で28採点区間を再判定できた。意味平均2.86/3、`lStart` p50 10.30秒・p95 24.32秒、8秒以内32%で、元のClaude判定（2.86/3、10.22秒、24.32秒、32%）と概ね一致した。Codex判定の4バッチには約7分を要した。これは**テキスト判定経路の動作確認**であり、OpenAI系の判定器による自己評価バイアスがなくなったことを意味しない。

[公式のプレビュー制限](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations)では、ChatGPTプラン利用経路で音声入力・Transcription APIは非対応。従ってCodex app-serverだけで音声→英語音声の5分リプレイは置き換えられない。[ChatGPT契約者向けAPIクレジット](https://developers.openai.com/api/docs/guides/chatgpt-api-credits)は別の制度で、対象のPro $200プランは月$200、GPT-Live・Realtime APIにも適用される。ただし、契約7日以上、同じメール、API組織Owner、契約と組織のリンクが必要で、初回は請求期間の残日数で按分される。実際の付与を請求画面で確認するまでは、予算として計上しない。

同日、現在のアカウントの資格を読み取り確認すると `eligible:false` / `not_qualified` だった。購入済みAPI残高をPro特典と混同しない。判定理由の詳細は表示されていないため、音声実験は既存の有料API枠からの支出として扱う。

## 再現手順と次の判定

`research/eval/README.md` の実時間リプレイ、参考原稿、判定コマンドを使う。音声・原稿・出力全文はGit管理外の研究資料を参照する。公開音声は上記のURLから取得可能。`--judge-backend codex --skip-asr` は**既存のv2 `output-words.json` が無いと失敗する**ため、意図しないASR課金は発生しない。ゼロAPI費用の下見には `--judge-backend codex --word-source subtitle` を指定し、遅延値は発話開始の評価に用いない。

次の判定ではJ-WAVE窓の訳音声を別系統の音声認識または聴取で照合し、字幕代理時刻と音声時刻を混ぜない。プロンプト改善を採用する閾値は、少なくとも独立した複数録音・複数反復で重大な意味誤りを増やさず、p95の改善が再現することとする。

## 重要事実が実際に訳音声へ出るまで（2026-10-29 追試）

公開演説の同一5分窓から、金額・期間・地名・否定など7件を選び、原音声と訳音声のASR単語時刻を対応づけた。`L_fact = 英語で事実を話し始めた時刻 − 日本語でその事実を言い終えた時刻`。誤訳や欠落は「速く訳せた」件数に入れず、別に数える。測定コードとannotation形式は[評価ハーネス](../research/eval/README.md#重要事実の音声遅延-l_fact)に追加した。

| 同一7事実、各エンジン1run | 正しく訳出し時刻も対応 | 誤訳 | 欠落 | 正しい事実の`L_fact` p50 / p95 |
|---|---:|---:|---:|---:|
| GPT-Live `plain-q` | 7 | 0 | 0 | 13.83秒 / 23.51秒 |
| Qwen3.8 LiveTranslate既定 | 5 | 1 | 1 | 5.45秒 / 10.51秒 |

Qwenの誤訳は将来の5年間を過去の5年間として述べた箇所、欠落は地名の箇所。Qwenの正しい事実は比較的早いが、**誤った事実を早く話しても通訳品質の改善には数えられない**。GPT-Liveの長い遅延には、先行区間の訳を話してから当該事実を話す時間も含まれる。選んだ7件だけの診断であり、全区間のp95ではない。日本語は`whisper-1`、英語訳音声はローカルwhisper.cppの語時刻で、両者の本文・時刻を文字ベースで見直したが音声を人が校正していない（`asr-reviewed`）。正確な耳到達時刻や人手の意味採点ではない。annotationと個別対応はGit管理外の研究フォルダに置く。

## DeepL Voice比較の利用条件

[DeepL Voice APIの公式説明](https://developers.deepl.com/docs/voice/overview)は、原文転写・訳文・訳音声を単一WebSocket sessionから受けられ、`spoken_terms`と訳語glossaryを別々に設定できるとしている。日本語では途中転写の区切り方により用語一致が漏れ得るため、用語の命中率を訳音声で測る必要がある。一方、[DeepLのプラン説明](https://support.deepl.com/hc/en-us/articles/360021200939-DeepL-API-plans)で無料Developer枠に音声翻訳はなく、[契約条件](https://www.deepl.com/en/pro-license)ではspeech-to-speechを対象プランに限定する。現在のPC環境にはDeepL APIキーがない。**訳音声を同条件で試せる契約資格を確認するまで、DeepLの精度や速度を既定候補として評価しない。**

## 独立した日本語読み上げ75件の誤訳監査（2026-10-29）

### 資料と再現条件

[京都大学NLPのCoVoST 2 Native Japanese](https://github.com/ku-nlp/covost2NativeJa)は日本語の音声、日本語原文、対応する英語参考訳を公開している（CC BY 4.0）。test splitから、モデル出力を見る前に固定seedで75クリップを抽出した。質問15、否定16、数値16、条件16、不動産関連4、その他8を**文字列で抽出する枠**とし、分類の偽陽性を個別監査で訂正した。2人の話者が大半を占める1～6秒の読み上げ文を約1.565秒の無音でつなぎ、5分のWAVを作成した。元データの英訳にも主語や語義がずれる例があるため、判定は日本語原文を優先した。

同一のWAVを200 msずつ実時間で3つの単一セッションへ入力した。各モデルの英語字幕全文と訳音声をGit管理外へ保存し、訳音声をローカルWhisper `small.en` で再文字起こしした。字幕との語一致率はGPT-Live 98.6%、OpenAI Translate 97.1%、Qwen 99.4%。疑わしい日本語9件は別の `whisper-1` でも転記し、原音声の認識と英訳の誤りを分けて調べた。日本語・英語・参考訳の75行対照表、音声、出典情報、個別判定はGit管理外の `niho-translate-research-private/public-audio/covost2-native-ja/evaluation-20261029/` に置く。

| 同一75件・各1run | 訳音声ASRによる自動意味平均 / 3 | `L_start` p50 / p95 | 8秒以内 | 理想再生キュー最大 |
|---|---:|---:|---:|---:|
| GPT-Live `plain-q` | 2.59 | 3.55 / 5.84秒 | 100% | 0.69秒 |
| OpenAI Realtime Translate | 2.12 | 2.62 / 5.38秒 | 93% | 0.59秒 |
| Qwen3.8 LiveTranslate | 2.84 | 3.98 / 6.67秒 | 100% | 5.62秒 |

`L_start` は日本語クリップ開始から対応する英語**音声**の語頭まで。自動語対応は誤った英訳にも時刻を付けうるため、8秒以内を「正しく8秒以内」と読み替えない。意味判定モデルは境界の語を落として低く採点した例と、疑問を陳述にした箇所を見逃した例があり、**平均値は人手確定の正答率ではない**。訳音声自体を人が聴取して全件校正した結果でもない。

原文と訳文を個別に読むと、GPT-Liveでは原文の人名を職業名へ、2匹の犬の場所を別の場所へ、風邪を風へ、負債の償却を全く別の行為へ変えた。これらの多くはGPT-Liveの日本語字幕にも現れ、**原音声の聞き取り段階の誤り**が主因と考えられる。一方、別ASRも聞き違えた文があり、録音が難しい例を単純なモデル誤訳件数に含めない。Qwenはこれらの短文を概ね正しく訳したが、質問を陳述にした例、否定の程度を強めた例、話者の行為を相手への指示へ変えた例が残った。OpenAI Realtime Translateには質問・陳述の欠落と、主体・原因・固有語の大きな取り違えが複数あった。

**製品既定は変更しない。** Qwenはこの短文群では最良だが、同日の別の[連続した公開音声5分比較](#連続5分窓の結果)ではGPT-Liveより欠落が多い窓があった。さらに[自然な対談5分](#自然な日本語対談5分の比較と構成判断2026-10-30)で再生待ちが蓄積した。評価原稿から拾った単語をそのまま用語集へ渡す試験は漏洩になるため行わない。代わりに会話前に分かる地名・不動産用語の短い背景だけを別条件で試し、質問・否定・金額・主体の誤りを速度より優先して比較する。

## 自然な日本語対談5分の比較と構成判断（2026-10-30）

### 同じ原音声・訳音声で比較

[声庭（Koniwa）](https://github.com/koniwa/koniwa)がCC BY 4.0で公開する、尼崎市のラジオ対談（2011年）の76.5～376.5秒を使った。市長と司会者の質問・回答が入り、[時刻付き日本語転記](https://github.com/koniwa/koniwa/blob/master/data/amagasaki/amagasaki__2011_04_20.json)がある。公開転記が覆う発話時間は約294/300秒（98%）。読み上げ短文75件を無音でつないだ前節の約61%と違い、訳音声の再生待ちが蓄積するかを調べられる。音声は24 kHz PCMへ変換し、同じ200 msフレーム・実時間送信・8秒の後続無音で再生した。元音声・転記・英訳字幕・訳音声・語時刻・評価正本はGit管理外の `niho-translate-research-private/public-audio/amagasaki-20110420/` と `niho-translate-research-private/eval/runs/` に置いた。

公開転記からモデル出力を見る前に25の意味単位・37の重要事実を固定。現行`gpt-live-1 plain-q`、Qwen3.8 LiveTranslate既定の`speaker_detection`、[公式の別区切り方式](https://docs.modelstudio.console.alibabacloud.com/en/model-studio/live-translator-client-events)である`server_vad`を各1runで比較した。英語**訳音声**を同じローカルWhisper `small.en`で語時刻化し、同じ小型判定器 `gpt-5.4-mini` で意味を暫定採点した。訳音声ASRとモデル字幕の語一致率は順に96.2%、97.8%、97.5%。この一致は音声の人手聴取による正解保証ではない。

| 対談5分・各1run | 自動意味平均 / 3 | 生成英語音声 | 理想再生待ち最大 | 音声`L_start` p50 / p95 | 8秒以内率 |
|---|---:|---:|---:|---:|---:|
| GPT-Live `plain-q` | 2.917 | 302.26秒 | 0.39秒 | 7.07 / 11.62秒 | 58% |
| Qwen `speaker_detection` | 2.833 | 382.80秒 | 85.59秒 | 68.63 / 84.71秒 | 21% |
| Qwen `server_vad` | 2.833 | 335.28秒 | 38.55秒 | 18.09 / 38.91秒 | 21% |

`L_start`の分母は採点対象24区間。Qwenの`speaker_detection`では、元音声・公開転記にない先行内容を90～120秒頃の**原文字幕と訳音声の双方**に繰り返した。送信側のフレーム遅れ最大は38 msで、同じWAVのGPT-Liveには繰り返しが無い。`server_vad`の1回では繰り返しが消えたが、5分の入力より35秒長い訳音声を生成して再生待ちが約39秒に増えた。区切り方式が繰り返しを防ぐかは1runでは断定できないが、どちらも連続対談の5～8秒目標を満たさない。

**会話の途中での遅延増加を確認した。** 日本語の2つ目の開催場所質問は原音声178.1秒に始まり、180.5秒に終わる。対応する英語訳音声の *where* の語頭はGPT-Live 184.45秒、Qwen既定251.39秒、Qwen `server_vad` 199.86秒。発話開始からそれぞれ6.35秒、73.29秒、21.76秒で、質問を言い終えてから3.95秒、70.89秒、19.36秒。英語字幕の到着ではなく、訳音声の理想再生位置で測った。実イヤホンへの追加遅延は未測定。

自動の意味平均だけでは重大な違いを見逃す。Qwen既定は「車座集会」を *car-seat gathering* と訳し、両方式は5月に**これから開催する**第1回を一度 *we held* と過去形で述べた。後続の未来形は、既に聞いた過去形を取り消せない。GPT-Liveは同語を *Kuruma-za Shukai* とローマ字にしたため、後続の説明で趣旨は分かるが、用語単体では *roundtable meeting* の方が明瞭。これらの誤りは小型判定器の事実誤り件数に表れなかった。一方、Qwenの公開日本語字幕と参考原稿の単純な正規化編集距離は既定28.4%、`server_vad`12.9%、GPT-Live11.9%。既定の大きい値は上記の繰り返しを含む。公開原稿の表記差・言い淀みも数えるため、厳密な人手CERではない。

### 現時点の設計判断と次の実験

**精度優先の製品既定は`gpt-live-1 plain-q`の単一音声セッションを維持する。** この自然対談では重要事実37件を小型判定器がすべて保持と判定し、再生キューの増大もなかった。別の短文75件ではGPT-Liveに聞き取り誤りがあるため、「全場面で最良」「製品品質が完成」とは言わない。平均点の差と遅延は各条件1runで、日英話者による音声校正も未了。特に対談のp95 11.62秒は5～8秒目標を超える。Qwenへの既定切替や、会話途中での自動モデル切替は行わない。後者は話者文脈と未再生音声の引き継ぎも必要になる。

PCで続ける優先順は次の通り。

1. 公開・私有の**別話者の自然な対談**を含めて、質問・否定・数字・主体・固有名詞を日英話者が訳音声で校正する。モデル字幕と別ASRだけで合格にしない。公開原稿を事前の用語指定へ流す評価リークを避ける。
2. 現行GPT-Liveで、会話**前に分かる**短い背景と少数の固有名詞、公式の短い通訳指示、簡潔な英語化をそれぞれ単独で比較する。誤り・訳抜け・原文にない事実を増やさない条件だけ、独立した複数録音で反復する。早出し指示と背景の既定化は既存の比較で再現性が不足している。
3. `L_start`と、日本語で事実が確定した時刻から英語音声でその事実を話すまでの`L_fact`を、再生待ち込みの語時刻で測る。英語の生成量・再生キュー・語対応失敗を別に記録し、8秒達成率の分母に未対応区間を残す。
4. 別APIの調達は品質上の未解決に直接効く場合だけ行う。DeepL Voiceは契約資格がまだ無く、Qwenは区切り方式を変えても本録音の再生待ちが大きい。多段の文字起こし→翻訳→音声合成は現行の基準より意味と速度の両方で勝つまでは製品経路に戻さない。

この結果から先に製品コードへ入れるべき新しいモデル切替・出力倍速・音声の強制間引きはない。特にQwenの長い訳音声を単純に捨てれば重要な発言まで失う。次の実装判断は、上記の独立した人手判定と、後日行うiPhone・イヤホンの耳到達時刻測定を条件にする。
